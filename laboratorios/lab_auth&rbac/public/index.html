Laboratorio Sesiones y RBAC

  • ¿En qué consiste el ataque "A01: Control de Acceso Defectuoso" (Broken Access Control)?

    Este problema ocurre cuando la aplicación web no verifica correctamente si un usuario tiene permiso para ver ciertos datos o realizar una acción.

    Ejemplo: Un usuario cambia el número en la barra de direcciones de su navegador y el sistema le muestra la información privada de otra persona sin validar si tiene permiso.

  • ¿Cómo se puede prevenir este ataque?

    Para evitar este riesgo se deben aplicar las siguientes medidas:

    • Revisar permisos en el servidor.
    • Bloquear todo por defecto.
    • Usar identificadores difíciles de adivinar

RBAC

  • ¿En qué consiste el control de acceso basado en roles?

    El Control de Acceso Basado en Roles es un modelo de seguridad en el que los permisos se asignan a rolesy los usuarios reciben acceso a través de esos roles, no de forma individual.

  • Análisis comparativo: sistema con RBAC vs. sistema sin RBAC
    • Sistema con RBAC: GitHub

      GitHub aplica RBAC en sus organizaciones y repositorios mediante roles como Owner, Member, Maintainer, Triage, Write y Read.

      • Ventajas: Fácil de escalar; agregar un colaborador solo requiere asignarle un rol. Los permisos son predecibles .
      • Desventajas: Los roles predefinidos pueden ser demasiado amplios o demasiado restrictivos para casos de uso específicos.
    • Sistema sin RBAC: FTP tradicional

      Un servidor FTP clásico asigna permisos directamente a cada usuario sobre directorios específicos del sistema de archivos, sin un modelo de roles formal. Cada cuenta tiene su propio conjunto de reglas configuradas manualmente.

      • Ventajas: Control muy epsecifico por usuario, es útil cuando cada cuenta tiene necesidades completamente distintas.
      • Desventajas: Difícil de mantener a escala; actualizar permisos implica modificar cada cuenta individualmente. Mayor riesgo de inconsistencias y errores humanos. Sin visión global de quién puede hacer qué.
